# Version Management

How versions are numbered, bumped, and released in this project.

## Semantic Versioning

We follow [semver.org](https://semver.org) with game-studio conventions:

| Component | Format | When to bump |
|---|---|---|
| **Major** | `X.0.0` | First version that can be played start to finish, or a fundamental rework of the game's character |
| **Minor** | `X.Y.0` | New features, mechanics, areas, or systems — backwards-compatible |
| **Patch** | `X.Y.Z` | Bug fixes, balance, text, polish — no new features |

**Pre-release:** `v0.x` is used before the first finishable release. `v0.1` was the
security/stability pass. **`v1.0.0` is the first version a player can complete** — current.

## Where the version lives

| File | What it holds | How it's set |
|---|---|---|
| `blacklands.pro` | `SEMVER_MAJOR`, `SEMVER_MINOR`, `SEMVER_PATCH` | Edit these three variables |
| `version.h.in` | Template with `$$SEMVER` placeholder | Do not edit directly |
| `version.h` | Generated by qmake from `version.h.in` | Regenerated on every build |
| `src/core/ReleaseInfo.cpp` | `version()`, `versionHistory()`, `releaseNotes()` | Update `versionHistory()` on each release |
| `RELEASE_NOTES.md` | Human-readable changelog | One entry per release, newest first |
| `docs/ROADMAP_vX.Y.md` | Per-version roadmap | One file per version |

## Release checklist

When a version is ready to ship:

1. **Bump the version** in `blacklands.pro`:
   ```qmake
   SEMVER_MAJOR = 1   # current
   SEMVER_MINOR = 0   # or current
   SEMVER_PATCH = 0   # or current
   ```

2. **Regenerate and verify:**
   ```bash
   qmake6 -o Makefile blacklands.pro
   make -j$(nproc)
   grep SEMANTIC_VERSION version.h
   ```

3. **Run the verification gate:**
   ```bash
   make check
   ```
   All six core systems must have at least one external caller.

4. **Update `ReleaseInfo.cpp`:**
   - Add the new version to `versionHistory()` with date and summary
   - Update `releaseNotes()` if this version adds major features

5. **Write the release notes** in `RELEASE_NOTES.md`:
   - New entry at the top, under the version heading
   - What changed, why it mattered, how it was verified

6. **Commit:**
   ```bash
   git add -A
   git commit -m "v1.0.0: <short summary>"
   git tag v1.0.0
   ```

7. **Push:**
   ```bash
   git push origin main --tags
   ```

## Build number

The build number (`FULL_VERSION` in `version.h`) is derived from the git commit count:

```qmake
VERSION_INT = $$num_add($$COMMIT_COUNT, -1)
```

This is a monotonically increasing integer used by `UpdateManager` to compare builds. It is
**not** the semantic version — it's a build counter. The semantic version is `SEMANTIC_VERSION`.

## Pre-release vs release builds

`ReleaseInfo::isRelease()` returns `true` only when built with `QT_NO_DEBUG` (release mode).
Debug builds are considered pre-release regardless of version number.

```cpp
bool ReleaseInfo::isRelease() {
#ifdef QT_NO_DEBUG
    return true;
#else
    return false;
#endif
}
```

## Deprecation policy

- **Major versions** may break save compatibility, remove features, or change core mechanics.
- **Minor versions** must remain backwards-compatible with saves from the same major version.
- **Patch versions** must not change any behaviour — fixes only.

## Save compatibility

Saves are versioned with a `SaveVersion` field. When loading:

1. Check `SaveVersion` against the current version.
2. If older, run migrations.
3. If newer, refuse to load with a clear error.

See `gameStateManager.cpp` for the current migration logic.
